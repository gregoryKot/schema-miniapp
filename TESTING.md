# Тестирование миниаппа

Цель — **каждая строчка логики под тестом**. Достигаем её не разом, а по правилу
храповика: новый или изменённый код приходит уже с тестом, покрытие только растёт.

Бэкенд (NestJS) тестируется отдельно — см. `../../CLAUDE.md` и `*.spec.ts` в `src/`.
Этот файл — про фронтенд миниаппа.

---

## Главное правило (НЕ НАРУШАТЬ)

> **Пишешь или меняешь код → в том же изменении пишешь тест.**

- Новая функция/хелпер/хук → тест в том же PR. Без исключений.
- Чинишь баг → сначала тест, который падает на баге, потом фикс. Тест защищает от регрессии.
- Меняешь поведение → обнови тест так, чтобы он проверял **новое** поведение.
- «Потом допишу тесты» = не дописываются никогда. Тест — часть определения «готово».

Если строку нельзя протестировать — это сигнал, что логику надо вынести из
компонента в чистую функцию/хук (см. «Что и как тестировать»).

## Стек

| Инструмент | Зачем |
|-----------|-------|
| **Vitest** | раннер (тот же движок, что Vite — общий конфиг, быстро) |
| **@testing-library/react** | рендер компонентов, запросы по тому, что видит пользователь |
| **@testing-library/user-event** | реалистичные клики/ввод (не `fireEvent`) |
| **jsdom** | DOM в Node |
| **@vitest/coverage-v8** | покрытие |

Конфиг — `vitest.config.ts`. Глобальные моки/хелперы — `src/test/setup.ts`.

## Команды

```bash
npm test           # один прогон (CI, перед коммитом)
npm run test:watch # watch — держать открытым во время работы
npm run test:cov   # прогон + отчёт покрытия (текст + html в coverage/)
```

Один файл: `npm test -- src/utils/format.test.ts`
Один тест по имени: `npm test -- -t "склонение часов"`

## Где лежат тесты

Тест **рядом** с кодом, расширение `.test.ts` / `.test.tsx`:

```
src/utils/format.ts
src/utils/format.test.ts      ← здесь
src/components/NeedDial.tsx
src/components/NeedDial.test.tsx
```

(Бэкенд использует `.spec.ts` — разное расширение специально, чтобы раннеры
не цеплялись за чужие файлы.)

## Что и как тестировать

Приоритет — по риску и тестируемости, сверху вниз:

### 1. Чистые функции (`src/utils/`, хелперы) — обязаны быть 100%
Вход → выход, без DOM. Самые ценные и дешёвые тесты. Покрывай **граничные
случаи**: пустота, ноль, склонения, битый ввод, переходы через границы (месяц,
неделя, полночь). Время фиксируй через `vi.useFakeTimers()` + `setSystemTime`.

```ts
import { fmtDate } from './format';
it('убирает ведущий ноль у дня', () => {
  expect(fmtDate('2026-01-01')).toBe('1 янв');
});
```

### 2. Хуки (`use*`) — тестируй логику, не реализацию
Через `renderHook` из `@testing-library/react`. Мокай Telegram WebApp хелпером
`setTelegram(...)` из setup. Проверяй значение, реакцию на события, очистку.

### 3. Компоненты — поведение глазами пользователя
- Запрашивай по роли/тексту (`getByRole`, `getByText`), **не** по классам/`data-testid` без нужды.
- Действия — `userEvent`, затем проверка результата.
- Проверяй: что отрендерилось, что вызвался нужный колбэк, как меняется состояние, пустые/ошибочные состояния.
- **Не** проверяй инлайн-стили и точные пиксели — это хрупко и не про поведение.

```tsx
it('вызывает onClose по кнопке Назад', async () => {
  const onClose = vi.fn();
  render(<NoteSheet onClose={onClose} />);
  await userEvent.click(screen.getByRole('button', { name: /назад/i }));
  expect(onClose).toHaveBeenCalledOnce();
});
```

### 4. API-слой (`src/api.ts`)
Мокай `fetch` (`vi.stubGlobal('fetch', ...)`). Проверяй: правильный URL/метод/тело,
заголовки авторизации (initData), обработку не-2xx ответов, парсинг.
**Не** ходи в реальную сеть.

### Не тестируем
- Чистые данные без логики: `needData.ts`, `aboutData.ts`, `schemaTherapyData.ts` (исключены в конфиге).
- Точные стили, верстку в пикселях, цвета (это ловит дизайн-ревью, не unit-тест).
- Сам Telegram SDK / сторонние либы.

## Правила хорошего теста

- **Имя описывает поведение**, не реализацию: `'возвращает 0, когда нет оценок'`, а не `'тест getConsecutiveDays'`. Пиши на русском — как остальной проект.
- **Один тест — одна мысль.** Несколько `expect` об одном поведении — ок; проверять три разных вещи в одном `it` — нет.
- **Изоляция.** Тест не зависит от порядка и от других тестов. `localStorage` и DOM чистятся в `afterEach` (уже настроено в setup). Время — через fake timers, всегда возвращай реальное в `afterEach`.
- **Arrange–Act–Assert.** Подготовка → действие → проверка, визуально разделяй.
- **Без логики в тесте.** Никаких `if`/циклов вокруг `expect`. Нужно много кейсов — `it.each`.
- **Детерминизм.** Ноль зависимости от текущей даты, случайностей, сети, реального времени. Замокай.
- **Тест на баг падает до фикса.** Написал фикс — сначала убедись, что тест без фикса красный.

## Покрытие и храповик

`npm run test:cov` показывает честную картину (включая файлы без тестов — `all: true`).

Пороги в `vitest.config.ts → coverage.thresholds`. Политика:

1. Цифры **только растут**. Понизить порог нельзя — это значит откатить дисциплину.
2. Добавил тесты, подняв реальное покрытие — **подними и порог** до нового уровня (с небольшим запасом вниз, чтобы флуктуации не роняли CI).
3. Целевые ориентиры: `src/utils/**` и `src/api.ts` → **100%**; хуки → **100% логики**; компоненты → ключевые сценарии (рендер, колбэки, пустые/ошибочные состояния).
4. Низкое покрытие файла — не повод снижать планку, а список незакрытых строк = твой бэклог тестов.

Старт: пороги на 0 (честно — покрыты только утилиты). По мере покрытия — поднимаем.

## Перед коммитом

```bash
npm test            # всё зелёное
npm run build       # tsc проходит (тесты в строгом TS)
```

Красные тесты не коммитим. `.skip` / закомментированный тест без причины и тикета — запрещён.
